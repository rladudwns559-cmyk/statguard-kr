# StatGuard CSV 입력과 계산 조건 확인

이번 단계는 기존 WHEN2WARN 화면에 CSV 파일 선택, 미리보기, 계산 조건 확인을 연결한다. 주소는 `/statguard`다. 기존 AI 답변 검증과 Developer Console 메뉴에 진입 링크를 추가했다. 숫자 계산 실행·주장 비교는 다음 단계이며, 화면의 ‘조건 확인 완료’는 계산 결과나 사실 검증 판정이 아니다.

## 사용 방법

1. `/statguard`에서 CSV 한 개를 선택하거나 ‘예제 CSV로 시작’을 누른다. 예제는 기존 오프라인 개발 사례와 같은 합성 방문자 표이며 실측 자료가 아니다.
2. 미리보기에서 열 이름·문자·빈 셀이 의도대로 보이는지 확인한다. 최대 10행을 표시하며 조건 검사는 전체 행을 대상으로 한다.
3. 합계·평균·증감률 중 하나와 숫자 열을 고른다. 원래 단위는 자료 설명을 보고 직접 입력한다. 단위는 자동 추정하지 않는다.
4. 필요하면 선택 범위를 지정한다. 서로 다른 열의 정확한 문자열 일치 조건을 최대 4개까지 AND로 결합한다. 앞자리 0·대소문자·공백을 보존하며 빈 값 입력은 실제 빈 문자열을 선택한다.
5. 증감률에는 별도 기준 범위를 지정한다. 선택 행과 기준 행이 겹치거나 기준 합계가 0 이하이면 확인을 막는다. 예정 계산은 `(선택 합계 - 기준 합계) / 기준 합계 × 100`이다.
6. 빈 숫자 값의 중단·명시적 제외 정책을 확인하고 확인란을 체크한 뒤 ‘이 조건으로 확인’을 누른다. 조건·자료·인코딩이 바뀌면 확인 상태를 해제한다.

## 데이터 처리 경계

- 파일 선택은 로컬 브라우저의 FileReader로 읽는 동작이다. 서버 업로드 endpoint, DB, 파일 보관 기능을 추가하지 않았다. 외부 GPT·검색 서비스에도 전달하지 않는다.
- 원본 파일명과 미리보기는 React 문자열로 렌더링한다. HTML·수식·임의 코드는 실행하지 않는다.
- React 메모리와 브라우저 파일 입력에만 자료가 남는다. 새로고침·이동·자료 비우기로 작업 상태를 버린다. localStorage·sessionStorage·IndexedDB·서비스 워커에 CSV를 기록하지 않는다. 메모리의 포렌식 삭제나 운영체제의 원본 파일 삭제를 보장하지 않는다.
- 이 경로는 계정 데이터에 접근하지 않는 브라우저 도구이므로 로그인 없이 열 수 있다. 기존 `/ask`, `/projects`, `/runs`의 인증·인가 동작은 변경하지 않았다. Supabase SDK·키·DB 정책도 변경하지 않았다.
- 기존 계산 코어·연구 자료·평가 runner는 변경하지 않았다. 코어의 6개 연산 계열은 그대로이며, 이번 화면에서는 일정 관리를 위해 3개 연산의 조건만 제공한다.

## 제한과 엔진 연결 계약

크기 1 MiB, 데이터 10,000행, 64열, 셀 512자까지 허용한다. UTF-8/BOM을 우선 시도하고 실패하면 브라우저의 `euc-kr` 디코더를 통한 CP949 호환 해석을 시도한다. 문자 해석이 의도와 일치하는지는 미리보기로 확인해야 한다. 이 브라우저 인코딩 이름은 Python `cp949`와 모든 바이트에서 같다고 보장하지 않는다.

중복·빈·양끝 공백 header, 행 폭 불일치, 빈 물리 행, 제어 문자, 잘못된 따옴표를 거부한다. 따옴표 안의 쉼표·개행·중복 따옴표는 허용한다. Python CSV reader보다 더 엄격한 따옴표 입력 부분집합이며, 기존 Python parser의 계약을 바꾸지 않았다.

숫자는 기존 코어와 같은 제한의 일반 십진수 표기를 사전 검사한다. 올바르게 묶은 천 단위 쉼표와 음수를 허용한다. 지수 표기·단위 접미사·수식·무한대·NaN·18자리 초과 정수부·6자리 초과 소수부는 거부한다. 기준 양수 여부에만 정수 micro-unit 합산을 사용하고, 부동소수점으로 증감률 결과를 계산하지 않는다.

확정 조건 명세에는 원본 `source_sha256`, 사용자 지정 units, 기존 `CalculationSpec.from_mapping` 형태의 spec이 있다. 이것은 계산 코어의 `dataset_version`이나 `calculation_id`가 아니다. 후속 계산 연결에서는 원본 bytes를 Python 코어로 다시 읽고 조건·단위를 다시 검증하여 실제 버전과 계산 ID를 생성해야 한다. 브라우저의 ‘확인’ 상태를 서버의 검증 결과로 신뢰하지 않는다. 과거 평가기의 guarded persistence 계약과도 별개다.

## 로컬 확인과 검증

개발 확인 주소는 `http://127.0.0.1:5173/statguard`다. 이번 확인 서버는 비공개 환경파일을 읽지 않으며 Supabase와 provider 설정을 비워 두었다. 기존 로그인 화면은 이 확인 서버에서 비활성 상태로 표시될 수 있다. 운영 사이트와 운영 설정은 변경하지 않았다. PC나 확인 서버가 종료되면 이 로컬 주소는 다시 실행해야 한다.

검증 기록은 `artifacts/statguard_csv_workspace_v0.1/`에 있다. 새 테스트 49개와 기존 프런트엔드 119개, 합계 168개가 통과했다. 기존 계산 코어 83개와 trajectory 기본 2개도 각각 통과했다. TypeScript 검사와 비공개 환경파일을 읽지 않는 로컬 build가 성공했다. build는 배포가 아니다.

첫 테스트 시도는 샌드박스 임시 캐시 rename 권한 오류로 테스트 본문을 실행하지 못했다. 같은 환경 분리 설정으로 재실행한 전체 프런트엔드 168개는 모두 통과했고 skip은 0이다. 첫 브라우저 검사에서 모바일 넘침을 발견해 새 화면 CSS만 수정했다. 두 번째는 로그인 lazy 화면의 로딩을 기다리지 않은 검사 절차를 수정했다. 최종 브라우저 점검 17개가 통과했다. 최초·재검사 기록을 각각 보존했다.

실제 파일 선택, UTF-8·CP949 한글, 10행 미리보기, 전체 행 검사, 조건 확정·해제, 잘못된 새 파일로 교체 시 이전 결과 제거, 메모리 상태 비보존, 데스크톱·390px 화면 너비를 점검했다. 외부 요청·API 요청·페이지 JavaScript 오류는 각각 0이다. 모바일 크기 점검은 데스크톱 Edge에서 했으며 실제 휴대전화 터치·키보드는 미검증이다. 전체 과거 backend/evaluator 테스트는 이번 프런트엔드 변경 범위에서 실행하지 않았다.

기존 975개 기준 파일 중 메뉴·진입 연결 3개만 승인 범위에서 변경했고 나머지 972개는 SHA-256이 같다. 과거 v0.7 RED, 2/8 중단, 03 원인 미확정 및 evaluator 판정은 그대로다.
