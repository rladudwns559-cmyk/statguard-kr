# 큰 공개 모델·확대 문항 벤치마크 v0.5 프로토콜 (실행 전 고정)

작성: 2026-11-25. 답변·채점은 외부 GPU 서버의 Ollama 0.40.18에서 공개 모델로 한다(API 비용 없음). 결과를 본 뒤 조건·문구·지표를 바꾸지 않으며, 바꾸면 ‘변경 기록’에 남긴다.

## 1. 질문

v0.4의 두 약점을 확인한다.
1. **작은 모델이라 그런가?** 큰 공개 모델(27B~70B)의 답에서도 StatGuard 최종값 규칙이 통과시킨 답 중 오답이 거의 없는가, 그리고 큰 공개 모델 심판보다 적은가?
2. **표본이 작아서인가?** 문항을 474개로 늘렸을 때 심판 대비 차이와 근거 교정(S) 대 재확인(R) 차이가 통계적으로 유의한가?
3. v0.4에서 찾은 한계(질문과 다른 대상을 고르고 그 값은 정확히 읽은 오답)가 큰 모델에서도 나타나는가?

## 2. 문항 (`build.py`, 표본 추출 없이 전수 생성)

v0.4와 같은 공개 표 5종(176개국 지표, 시애틀 2023 일별 365행, 대한민국 2014~2023, 시애틀 2023 월별 강수량, 마우나로아 2024 CO2)에서 **템플릿 조합을 모두** 만든다(무작위 추출 없음).
- 176개국: 행이 3개 이상인 지역·소득그룹 10개 × (총인구 합계·평균·중앙값·표준편차·최댓값·최솟값, 실업률·1인당GDP·기대수명의 평균·중앙값·표준편차·최댓값·최솟값) = 210개, 그룹별 총인구 비율 11개
- 시애틀 일별: 12개월 × 9종(강수량 합계·평균·최댓값, 일 최고기온 평균·최댓값·최솟값, 일 최저기온 평균·최댓값·최솟값) = 108개, 기간 범위 12개, 연간 열 3개 × 통계 4종 = 12개
- 대한민국: 연도 쌍 45개의 총인구 증감률, 연도 구간(2년 이상) 36개의 실업률 평균, 10개 연도 × 2개 열 조회 20개
- 월별 표: 시애틀 강수량 기간 합계 6개, CO2 기간 평균 6개
- 자료로 답할 수 없는 문항 8개(v0.4와 같은 문장)

합계 **474개**(v0.4의 212개를 모두 포함하고 262개가 새 문항). 기대값은 StatGuard 엔진을 쓰지 않는 별도 Decimal 코드로 계산하고 채점에만 쓴다. 결과는 ‘v0.4와 겹치지 않는 262개’(`in_v04 = false`)도 따로 보고한다.

## 3. 답변 모델과 설정

| 모델 | 회사 | 비고 |
|---|---|---|
| qwen2.5:32b | 알리바바 | 4비트(Ollama 기본) |
| gemma3:27b | 구글 | 〃 |
| llama3.3:70b | 메타 | 〃, GPU 2장 |

- 지시문·입력·판정 규칙·교정 문구는 v0.4와 같다(`../statguard_benchmark_v0.4_local/run_local.py`의 것을 그대로 씀). Ollama 옵션도 같다: `num_ctx` 16384, `temperature` 0, `seed` 7, `num_predict` 1024.
- 문항당 1회. 같은 요청은 캐시에서 다시 쓴다. 호출마다 입력 토큰 수와 컴퓨터 이름을 기록한다.
- **실행 순서(시간이 모자라면 앞 단계까지의 결과만 보고):** ① 세 모델 답변 → ② 심판 채점 → ③ 교정(R·S 최대 2라운드).

## 4. 검증과 판정

- 검증기: 현재 엔진(추출기 v0.7.1). 답변 판정은 **최종값 규칙**을 주 규칙으로, 사전 등록 규칙을 보조로 보고한다(`run_local.final_rule`, `run_local.decide`).
- 정답 여부: `../statguard_benchmark_v0.3/evaluate.py`의 `final_value`·`is_correct`.
- 심판: **qwen2.5:32b**(v0.4와 같은 지시문·JSON 형식·옵션). qwen2.5:32b는 답변 모델이기도 하므로 **자기 답을 채점한 부분은 따로** 보고한다. 형식이 깨진 응답은 HOLD. 입력 토큰이 16,384 이상인 판정은 잘린 것으로 보고 HOLD로 처리한다.
- 결합 방식: 최종값 규칙이 PASS나 FLAG면 그대로, HOLD면 심판 판정.

## 5. 주 지표와 검정 (미리 정함)

1. **통과 중 오답**: StatGuard 최종값 규칙 vs 심판 단독 vs 결합. 모델별·전체, 95% 상한(Clopper–Pearson). 통과 중 오답 **비율**의 차이(StatGuard vs 심판, 전체)를 **Fisher 정확 검정(양측, α = 0.05)**으로 본다.
2. **근거 교정**: 계산 불일치(FLAG)로 잡힌 오답에 대해 S 1회 후 정답 vs R 1회 후 정답. 같은 답에 대한 짝지은 비교이므로 **McNemar 정확 검정(양측, α = 0.05)**. 모델별·전체 정답 수(원래 → R 2회 → S 2회)도 보고한다.
3. 통과 중 오답의 유형(질문과 다른 대상 선택 여부)을 문항 범주별로 센다.
4. 보조: 오답 중 FLAG, 정답을 FLAG(오경보), 보류 비율, 역추적·검산 결과, 응답 시간.

검정은 이 두 개만 하며, 다른 비교는 기술 통계로만 보고한다. 분석 코드(`analyze.py`)는 결과를 보기 전에 작성해 함께 고정했다(검정 함수는 이전 결과 Fisher p = 0.072를 그대로 재현함을 확인).

## 6. 해석 한계

- 4비트 양자화 모델이고, 문항은 템플릿이라 실제 질문보다 단순하다. 같은 표 5종을 이전 실험에서도 썼다.
- 심판과 답변 모델 하나가 같다(qwen2.5:32b).
- 결과가 좋아도 나빠도 그대로 보고한다. 이 실험으로 엔진이나 규칙을 바꾸지 않는다.

## 변경 기록

- 2026-11-26, 결과를 받은 뒤(분석 코드 버그만 수정, 판정 규칙·검정·데이터는 그대로): `run.items()`가 `questions.json`의 `in_v04`를 넘기지 않아 ‘v0.4와 겹치지 않는 문항(new_only)’ 표가 전체와 같게 나왔다(서버에서 팀원이 발견). `analyze.py`가 `questions.json`에서 직접 읽도록 고쳤다. 미리 정한 두 검정은 전체(all) 기준이라 영향이 없다. 같은 때 첫 답변이 출력 한도(1,024토큰)에서 끊긴 경우를 따로 세는 표를 추가했다(기술 통계만; 서버 기록상 끊긴 호출은 교정 포함 llama3.3 55건·gemma3 13건이며, 첫 답변은 llama3.3 11건·gemma3 5건으로 모두 형식 오류·오답이고 StatGuard가 통과시킨 것은 없다).
