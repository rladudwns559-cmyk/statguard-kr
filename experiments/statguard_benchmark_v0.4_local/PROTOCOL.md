# 로컬 공개 모델 벤치마크 v0.4 프로토콜 (실행 전 고정)

작성: 2026-11-25. 답변은 이 PC에서 Ollama로 돌리는 공개 모델이 쓴다(API 비용 없음). 결과를 본 뒤 조건·문구·지표를 바꾸지 않으며, 바꾸면 ‘변경 기록’에 남긴다.

## 1. 질문

1. **일반화:** OpenAI가 아닌 회사의 공개 모델(알리바바·메타·구글)이 처음 보는 문항에 쓴 답에서도, StatGuard가 ‘통과’시킨 답 중 오답이 거의 없는가?
2. **사후 규칙의 새 데이터 검증:** 결과를 보고 만든 ‘최종값 규칙’과 미적용 추출기 v0.8이 새 문항·새 모델에서 어떻게 동작하는가?
3. **교정:** 재계산 근거(S)가 단순 재확인(R)보다 오답을 더 많이 고치는가(이 모델들에서도)?
4. 오류 역추적과 답변 속 계산 검산이 실제 새 오답에서 어떻게 동작하는가?

## 2. 문항 (`build.py`, 시드 20261125)

기존 공개 표 5종(176개국 지표, 시애틀 2023 일별 기상 365행, 대한민국 2014~2023, 시애틀 2023 월별 강수량, 마우나로아 2024 CO2) — 365행 이하만 쓴다(1,460행 표는 8GB 그래픽카드에서 입력이 너무 길어 제외). **새 문항 212개**: 합계·평균·중앙값·표본표준편차·최댓값·최솟값·비율·증감률·값 조회·기간 범위, 그리고 자료로 답할 수 없는 문항 8개. 기대값은 StatGuard 엔진을 쓰지 않는 별도 Decimal 코드로 계산했다. 기대값은 채점에만 쓰고 모델에게 주지 않는다.

## 4. 검증과 판정

- 검증기: 현재 엔진(추출기 v0.7.1, 기간 범위 지원), 비교용으로 v0.7(고정 사본)과 v0.8(`../statguard_extractor_v0.8/claims_v0_8.py`, 미적용판).
- 답변 판정 규칙 두 가지: 사전 등록 규칙(불일치 있으면 FLAG, 불일치 없이 일치가 하나라도 있으면 PASS, 그 외 HOLD)과 최종값 규칙(`../statguard_comparison_v0.1/analyze_final_rule.py`의 정의 그대로).
- 정답 여부: `../statguard_benchmark_v0.3/evaluate.py`의 `final_value`·`is_correct`.

## 5. 교정 (R·S)

`../statguard_correction_v0.1/PROTOCOL.md`와 같은 대상 선정·문구·최대 2라운드. S의 근거는 현재 엔진(v0.7.1) 결과로 만들고, 보류 사유 문구는 교정 실험의 고정 사본(`frozen/reasons_ko.json`)을 쓴다. 교정 요청은 답을 쓴 그 모델에게 보낸다.

## 6. 지표

- 모델별·전체: 정답률, 형식 오류 수, StatGuard 판정 분포, **통과 중 오답(주 지표)**과 95% 상한, 오답 중 FLAG, 정답을 FLAG(오경보).
- 판 비교(v0.7·v0.7.1·v0.8) × 규칙 비교(사전 등록·최종값).
- 교정: 원래 → R 1·2회 → S 1·2회 정답률, 불일치로 잡힌 오답의 고침 수, 망침 수.
- 역추적이 원인을 재현한 수, 검산이 잡은 수(정답 여부와 함께).
- 응답 시간(모델별 중앙값).

## 7. 해석 한계

- 4비트 양자화한 작은 모델이라 큰 모델과 결과가 다를 수 있다. 문항은 템플릿으로 만들어 실제 사용자 질문보다 단순하다.
- 같은 표 5종을 이전 실험에서도 썼다(문항은 새로 만듦).
- 이 실험에서 v0.8이나 최종값 규칙의 결과가 좋아도 바로 적용하지 않는다. 적용은 v0.7.1과 합친 판을 별도 계획서로 평가해 정한다.

## 8. 추가 (2026-11-25, 심판 결과를 보기 전에 고정): 큰 공개 모델 심판과 결합 방식

- **심판 모델:** qwen2.5:32b(Ollama 0.40.18 기본 4비트), 외부 GPU 서버에서 실행. 지시문·출력 형식(JSON `{verdict: 맞음/틀림/판단불가, reason}`)은 `../statguard_comparison_v0.1/run_comparison.py`의 LLM 심판과 같다. Ollama 구조화 출력(`format`=같은 스키마), `temperature` 0, `seed` 7, `num_ctx` 32768(1,460행 표 포함), `num_predict` 512. 형식이 깨진 응답은 HOLD.
- **채점 대상:** (a) 이 실험의 답 636개(모델 3종 × 212), (b) `statguard_comparison_v0.1`의 OpenAI 모델 답 360개(이전 gpt-6-luna 심판과 같은 답).
- **비교하는 방식:** ① 심판 단독(맞음=PASS), ② StatGuard 최종값 규칙, ③ **결합 방식** = StatGuard 최종값 규칙이 PASS나 FLAG면 그대로, HOLD면 심판 판정. (a)에는 현재 엔진(v0.7.1), (b)에는 이전 실험과 같은 v0.7 고정 사본을 쓴다.
- **지표:** 통과 수, 통과 중 오답(95% 상한), 오답 중 FLAG, 정답을 FLAG. (b)에서는 gpt-6-luna 심판 결과(통과 235개 중 오답 13개)와 나란히 보고한다.
- 결합 방식이 좋게 나와도 바로 웹에 적용하지 않는다(별도 계획서 필요).

## 변경 기록

- 2026-11-25, 교정 결과를 보기 전(답변 생성만 끝난 시점): 실행 시간 때문에 **실행 컴퓨터를 모델별로 나눈다.** qwen2.5:7b·gemma3:4b는 이 노트북(RTX 5050 8GB)에서 답변·교정을 모두 하고, llama3.1:8b는 답변 생성부터 교정까지 **외부 GPU 서버(RTX PRO 4500 Blackwell 32GB)에서 처음부터 다시** 한다(노트북에서 이미 만든 llama 답변은 쓰지 않고 `results/llama_laptop_backup/`에 따로 보관). 한 모델의 답변과 교정은 한 컴퓨터에서 끝낸다. Ollama 버전(0.40.18)·옵션·코드는 같게 하고, 서버의 GPU·버전 정보와 호출마다 컴퓨터 이름을 기록한다. 같은 설정이어도 GPU가 다르면 출력이 조금 다를 수 있어, 노트북과 서버의 llama 답변이 얼마나 같은지도 함께 보고한다.
- 2026-11-25, 심판 결과를 보기 전(서버에서 채점 575개 진행, 결과 파일은 아직 받지 않음): **심판 입력 길이 초과 처리.** `07_미국4개도시_2023_일별기상.csv`(1,460행)를 쓰는 비교 실험 답 63개는 입력이 약 4만 토큰으로, qwen2.5:32b의 학습 길이(32,768)와 `num_ctx` 32768을 넘어 Ollama가 HTTP 500을 냈다(8장의 “1,460행 표 포함”은 잘못된 예상). `num_ctx`를 늘리면 학습 길이를 넘는 위치를 읽게 되어 판정이 의미 없어지므로 늘리지 않는다. 이 63개는 심판에게 보내지 않고 **HOLD(심판 불가, `skipped: input_exceeds_judge_context`)**로 기록한다(기준: CSV·질문·답변 합계 30,000자 초과. 해당 63개는 최소 38,995자, 나머지 933개는 최대 12,327자). 지시문·옵션·나머지 입력은 그대로라 이미 받은 575개 캐시가 그대로 쓰인다. 그 밖의 서버 오류는 기록하지 않고 넘어가 다시 실행할 때 재시도한다. (b)의 보고에는 360개 전체(63개 HOLD 포함)와 07 표를 뺀 297개를 함께 싣는다. 이는 큰 공개 모델 심판이 긴 표를 읽지 못한다는 한계이며 StatGuard는 같은 63개를 재계산했다.
- 2026-11-25, 같은 날 추가(심판 결과는 아직 받지 않음): 서버 보고에 따르면 위 63개 중 **59개는 수정 전에 이미 채점됐다.** Ollama가 입력 앞부분을 잘라 낸 채(‘truncating input prompt’ 경고) 판정한 것이라 표 전체를 읽은 판정이 아니다. 따라서 분석에서는 **63개 모두를 HOLD(심판 불가)로 덮어쓴다.** 잘린 입력으로 나온 59개 판정은 결과 파일에 그대로 남기되 주 지표에 쓰지 않고, 투명성을 위해 별도 줄로만 보고한다. 주 지표에 쓰는 나머지 933개는 기록된 입력 토큰 수(`prompt_tokens`)가 32,768 미만인지 분석에서 확인한다.
- 2026-11-25, 서버 결과를 받은 뒤(분석 방법만, 판정 규칙은 그대로): 서버 결과는 `results_server_llama/`에 따로 두고 `run_local.py`(보고)와 `analyze_judge.py`가 두 폴더를 함께 읽는다(같은 요청은 같은 파일 이름이라 섞이지 않음). 서버 Ollama는 설정(32,768)과 달리 실제로 **16,384토큰에서 입력을 잘랐다**(잘린 판정의 `prompt_tokens`가 모두 16,386). 주 지표에 쓴 나머지 933개 판정은 입력이 최대 11,206토큰이라 잘리지 않았고, 분석 코드가 이를 하나씩 확인한다. 서버에서 한때 임시 실행기로 채점한 구간이 있었으나 요청 본문과 캐시는 `judge_local.py`와 같다(서버 보고, `judge_attempt1_error.log`).
